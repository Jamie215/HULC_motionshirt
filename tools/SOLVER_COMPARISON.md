# Pose solver comparison: default chain vs OpenSense

Which path gives better joint angles: our default chain (`calibrate_segments.py`
→ `metrics.py`) or OpenSim OpenSense (`opensense_ik.py`)? Assessed 2026-09-25
with OpenSim 4.6 and the Rajagopal 2015 OpenSense model, **after** the pipeline
fixes in the same change:

- auto neutral window (a placeholder montage window is rejected)
- facing from the elbow hinge when there is no torso node
- the wrist split in its palms-in neutral frame
- plausibility flags

**Verdict:** keep the default chain as the primary path. On the full montage the
two are equally accurate. On a no-torso montage the default chain is clearly
better on pro/supination. It also runs in under a second with no dependencies.
OpenSense stays useful as an optional cross-check and fit-quality signal
(`analyze_session.py run … --opensense-model PATH`).

## 1. Synthetic ground truth (`tools/compare_paths.py`)

The harness plays a protocol-shaped 40 s session on the model:

- neutral hold (palms facing the thighs)
- shoulder swing
- 4 curls (supinated)
- pro/supination with 65° abduction
- full swing with humeral rotation
- rest, with trunk sway throughout

Virtual nodes have random strap mountings, and the subject faces 37° off world
+Y. Both paths get identical node streams and the same calibration step. Truth
goes through the same `metrics.py` angle definitions.

- **clean:** 60 Hz, ~1° RMS slow sensor error
- **realistic:** 8.3 Hz (today's firmware), ~3° RMS slow error per strap
  (sensor + soft tissue), 50 ms clock offset on the distal nodes

RMS error, degrees (p95 in brackets):

| DOF | full, clean: default | full, clean: OpenSense | full, realistic: default | full, realistic: OpenSense |
|---|---|---|---|---|
| shoulder elevation | 2.7 (3.8) | **2.1** (2.7) | 6.0 (10.9) | **5.6** (9.9) |
| shoulder axial rotation | 0.8 (1.3) | 0.8 (1.3) | 4.7 (8.9) | 4.7 (8.9) |
| elbow flexion | 0.4 (0.6) | 0.3 (0.6) | 2.4 (4.2) | 2.4 (4.6) |
| elbow pro/sup | 1.5 (2.2) | **1.0** (1.4) | **2.1** (3.1) | 3.1 (5.1) |
| wrist flexion | **0.6** (1.1) | 1.0 (1.5) | **2.1** (4.3) | 2.3 (4.9) |
| wrist deviation | 0.5 (1.1) | 0.4 (0.9) | 5.1 (7.9) | 5.3 (8.3) |

The upper-arm + forearm montage (no torso; your capture) is scored against the
model's own joint coordinates. That scoring doesn't depend on any frame
choice (see note 2):

| elbow DOF | clean: default | clean: OpenSense | realistic: default | realistic: OpenSense |
|---|---|---|---|---|
| flexion | 1.6 | 1.2 | 4.4 | 4.7 |
| pro/sup | **1.9** | 8.1 | **4.5** | 9.2 |

Notes:
1. **With a torso node, the two are within about 1° everywhere.** OpenSense's
   joint constraints help a little in clean data. With realistic error the
   model has no edge, and the default chain is slightly better on pro/sup.
   Errors roughly double going from clean to realistic, and that comes from
   the input (8 Hz sampling, strap wobble, clock offset), not the solver.
2. **Without a torso node, OpenSense loses on pro/sup.** The facing comes from
   the elbow hinge, which lies in the elbow's own flexion plane. In this model
   that plane is 13° from the trunk's left-right axis (the recovered facing
   is 14° from the trunk's). The default chain zeroes each segment at the
   neutral hold and splits the elbow about that hinge, so the offset costs it
   nothing. OpenSense places its model assuming the facing is the trunk's.
   The 13° goes into the humerus placement, and forearm rotation is then
   misread (8–9° RMS).
3. **The setup favours OpenSense.** Truth is generated by the same model it
   fits, so its joint axes match exactly; a real arm's won't. The soft-tissue
   wobble is only a rough stand-in for that mismatch.
4. **Facing recovery:** from the torso, within 0.7° (clean) and 2° (realistic).
   From the elbow hinge, the 13–14° offset above is the hinge plane, not an
   error in finding it.

## 2. Real capture (upper arm + forearm, 2026-09-25)

The session: neutral hold, shoulder swing, curls, supination/abduction, then
the swing again. No ground truth, so this measures agreement and fit, not
accuracy.

| | default | OpenSense |
|---|---|---|
| neutral window | auto: 36.7–38.7 s (placeholder 1–4 s rejected) | same |
| facing | elbow hinge −45° (contrast 0.65) | same |
| elbow flexion ROM | −21…145° | −18…145° |
| pro/sup ROM | −80…100° | −83…92° |
| curls found | 5 clean 0→~140° cycles at 70–90 s | same |
| agreement, frame by frame | RMS 5.4° flexion, 2.3° pro/sup | — |
| fit residual (node vs solved skeleton) | — | median 5°, p95 20°; the >20° frames are fast motion |
| run time | < 1 s | ~35 s, plus `pip install opensim` and the model |

The two paths agree well on real data. OpenSense's residual is a useful
by-product: it marks the frames where the nodes disagree with any rigid
skeleton. On this capture those are the fast frames, where 8 Hz sampling and
the inter-node timing uncertainty (sync confidence 0.52) dominate.

## 3. Recommendations

1. **Default chain stays primary.** It is at least as accurate here, better
   without a torso node, dependency-free and instant.
2. **Use OpenSense as a QA pass** (`--opensense-model`): a second opinion on
   ROM, plus per-frame residuals that flag untrustworthy stretches. Don't use
   its joint angles on no-torso sessions until the hinge-vs-trunk offset is
   handled.
3. **The bigger accuracy lever is the input, not the solver.** The realistic
   condition doubles every error:
   - Raise the log rate from 10 Hz toward 30–60 Hz.
   - Keep nodes at full rate through the neutral hold.
   - Tighten straps.
4. **Real validation still needed:** an optical motion-capture or goniometer
   session, since both paths share the same calibration assumptions.

## Reproduce

```bash
pip install opensim
git clone --depth 1 --filter=blob:none --sparse https://github.com/opensim-org/opensim-models
(cd opensim-models && git sparse-checkout set Models/Rajagopal_OpenSense)
python tools/compare_paths.py --model \
    opensim-models/Models/Rajagopal_OpenSense/Rajagopal2015_opensense.osim
```
