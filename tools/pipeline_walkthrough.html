HULC Motion Shirt · data pipeline

From node quaternions to range of motion

Seven stages turn raw orientation logs off each IMU node into per-joint motion metrics. Four exist today; calibration is next; the metric and interface layers are still on paper. Each handoff below names the tool that runs it and the exact data it passes on.

01

Capture Built

Each IMU node logs its own segment's orientation. A BNO086 on a XIAO nRF52840, one per body segment, advertising as HULC-IMU-XXXX. The onboard stability classifier drives the state machine — IDLE → STATIC_POSTURE → ACTIVE_RECORDING — and quaternions are written to flash at ~10 Hz, with a 0.2 Hz heartbeat while still so stillness is recorded, not left as a gap.

On-flash record · 20 bytes, little-endian
uint32 timestamp_ms  float qw  float qx  float qy  float qz
one .bin log per node, timestamped on each node's own millis() clock
02

Offload Built

Bulk-transfer each node's log to a central over BLE after the session — no live streaming. A well-behaved central (phone / BlueZ) honors a fast connection interval and pulls ~20 KB/s, so a full flash comes off in minutes. Each node's log lands in its own file.

Per-node files
HULC-IMU-D067.bin   HULC-IMU-A1B2.bin   HULC-IMU-C3D4.bin  …
N independent logs, not yet on a shared clock
03

Reconcile & time-align Built

Put every node on one timeline. reconcile_nodes.py reduces each node to its mounting-invariant angular speed, cross-correlates the streams to recover the clock offset (and optional drift), and resamples all quaternions onto a shared grid. A Pearson r confidence (≥ 0.40) flags pairs that shared too little motion — the case a start-of-session sync gesture exists to cover.

aligned.csv · one shared clock, per-node columns
t_common_ms, n0_qw,n0_qx,n0_qy,n0_qz, n1_qw,n1_qx,n1_qy,n1_qz, …
aligned streams keyed by column n0, n1, … — but which body part is each?
04

Montage & capability resolve Built

Bind each column to a body segment, then resolve what's computable. A montage.json maps each n{i} column to a segment (with an optional landmark label and a calibrated flag). motion_capabilities.py reads it and reports which joints and metrics the placement supports — and blocks the rest, naming the missing node. A joint needs both its adjacent segments; bilateral activity asymmetry needs only a matching L/R pair.

montage node entry
{ "column":"n1", "segment":"upper_arm_r", "landmark":"right humerus", "calibrated":true }
a capability report: computable joints & metrics, each with its trust gates
You are here — calibration is the next build
05

Calibrate Next up

Turn relative orientation into anatomical angles. A node reports orientation in its own mounting frame, offset from anatomy by however the strap sat. A static neutral / N-pose (optionally plus a known functional move) defines each segment's anatomical frame. Until this exists, every angle the resolver lists is flagged relative-only — a real number, but not a clinical one. This is what gates ROM.

emits · calibration.json (per segment)
# quaternion offset: mounting frame → anatomical frame
upper_arm_r → q_anat_offset,  neutral captured @ t_common_ms [1000,4000]
aligned streams + segment map + anatomical zero — enough to compute a clinical angle
06

Metric plugins Planned

Functions over the aligned + calibrated stream. Each metric the resolver declared becomes a small plugin: joint angle series and ROM, movement smoothness, activity asymmetry (which arm is used more), posture dwell, rep count. ROM is just the first — the contract is already fixed, so adding one is filling in a function, not reworking the pipeline. Every value ships with its quality gates: dropout, sync_confidence, sensor_cal.

metric values + trust flags, per joint / per segment / per window
07

Interface & visualization Planned

The thing all of this feeds. Two modes: a live skeleton driven by the quaternions to sanity-check placement before a capture, and a post-hoc view — per-joint ROM arcs and angle traces, an upper-extremity heatmap, left/right asymmetry, posture-dwell histograms. Every value is rendered next to its confidence, so a low-trust number never reads as a clean one.

Worked example — the sparse two-node case

Two nodes, one on each upper arm, no torso; the left arm is worked hard, the right barely moves. This is exactly where alignment struggles and most joint metrics can't form — here's what stages 3–4 actually say about it.

montage.json2 nodes
n0 → upper_arm_l   (left, active)
n1 → upper_arm_r   (right, still)
torso → absent
capability reportresolved
shoulder_l / _r (ROM)✗ needs torso
elbow / wrist (ROM)✗ needs forearm/hand
per-arm elevation, speed✓ segment
activity_asymmetry_upper_arm✓ derived

The reconcile step returns a low-confidence offset here — the two arms share almost no motion to lock onto — so no joint angle would be trustworthy even with a torso node. But activity asymmetry is a session aggregate that doesn't need the sides time-aligned, so "the left arm is used far more than the right" survives as the one solid, useful answer this montage can give.
